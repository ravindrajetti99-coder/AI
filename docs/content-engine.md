# Content engine: syllabus, concept content, review and serving

Status: foundation shipped in PR #5 (SSC CGL). The AI generation engine that fills it is PR #6
(see the plan at the end of this file).

EduVerse serves exam courses on a **generate once → review → store → serve many** model. The
syllabus says exactly what an exam covers. Content for each concept is produced once (written by
an author, imported from previous papers, or generated by the AI engine), reviewed by a person,
stored, and then served unchanged to every learner. Learners never trigger generation in an exam
course, so every learner gets the same reviewed lesson, and the AI cost does not grow with the
number of learners.

## Layers

| Layer | Where | What |
| --- | --- | --- |
| Syllabus data | `apps/api/app/seed/syllabus/data/<course>/` | YAML: exam stages, subjects, chapters, topics, sub topics, concepts and what the author knows for sure (summaries, prerequisites, formulas, exam patterns, shortcuts, strategies) |
| Content model | `catalog`, `content`, `assessment` modules | `course_nodes` (keyed, tiered), `concepts`, `formulas`, `shortcuts`, `question_patterns`, `exam_strategies`, `questions` (pool, pattern, PYQ paper, stem hash), `pyq_sources`, `pyq_imports` |
| Review | content studio, `/admin/review-queue` | every lesson, question, flashcard, formula, shortcut, pattern and strategy starts `in_review` |
| Serving | `/concepts/{id}/lesson`, `/concepts/{id}/study-pack`, practice and mocks | verified content only for exam courses |
| Coverage | `/admin/courses/{slug}/coverage` | verified content against each concept's requirements, plus mock-pool readiness |

### Content depth

The hierarchy is **Subject → Chapter → Topic → Sub topic → Concept**, and below each concept
**Question pattern → Shortcut → Exam strategy**. The ten elements the course owner asked for map
onto the model like this:

| Element | Stored as |
| --- | --- |
| Concept explanation | lesson level 1 (beginner): `definition`, `explanation`, `examples`, `diagram` |
| Deep understanding | lesson level 3 (advanced) |
| Formula / rule | `formulas` (the formula sheet) |
| Solving method | lesson `solving_method` (numbered steps) and question solution steps |
| Short tricks | `shortcuts` with kind `shortcut` / `memory` / `approximation` |
| Alternative fast method | `shortcuts` with kind `alternative` / `elimination`, linked to the pattern it cracks |
| Common mistakes | lesson `common_mistakes`, shortcut `pitfalls`, the `mistakes` solution step |
| SSC exam pattern | `question_patterns` (frequency, tiers, difficulty, target time) |
| Previous-year question mapping | `questions.source = pyq` with `pyq_source_id` (paper) and `pattern_id`; the PYQ analysis in the study pack |
| Practice questions | `questions` in the `practice` pool; the `mock` pool is held back for full mocks |

Visual explanation (`diagram`, Mermaid), memory tricks (`memory_technique`) and the formula and
shortcut sheets are parts of the same records.

## Syllabus files

```
data/ssc-cgl/
  course.yaml            course, exam stages, content requirements, mock targets, course strategies
  exam_profiles.yaml     Tier 1 and Tier 2 (Paper I) patterns, dated with as_of and a verify note
  quant/subject.yaml     title, tiers, subject strategy, chapter order
  quant/percentage.yaml  chapter → topics → sub topics → concepts (+ formulas, patterns, shortcuts)
  reasoning/ english/ general-awareness/ computer/
```

The format is defined and validated by `app/seed/syllabus/schema.py` (unknown fields are errors)
and `reader.py` (cross-file checks: references resolve, keys fit their columns, tiers only narrow
going down the tree, prerequisites have no cycles, no chapter file is forgotten). Key points:

- **Keys.** Nodes have keys unique among siblings; the stored key is the dotted path
  (`quant.percentage.applications.successive`), so titles and order can change without losing
  anything. Concept slugs are global: the concept graph is shared by every course and mastery
  earned once counts everywhere. Formula, pattern and shortcut keys are local to their concept
  and stored as `<concept>:<key>`.
- **Reuse.** `ref: <slug>` places a concept another course defines (e.g. the arithmetic pilot's
  `percentage-basics`); a ref may add formulas, patterns and shortcuts but not change the title,
  summary or prerequisites.
- **Tiers.** `tiers` (exam stages from `exam_profiles.yaml`) inherit down the tree and may only
  narrow (Computer Knowledge is Tier 2 only).
- **Authored status.** Items written in the files load as `authored_status` (`in_review`): they
  go through the same review as generated content. Changing an item's text in the files sends it
  back to review; removing it retires it; an unchanged item keeps whatever review decided, and a
  rejected item stays rejected. Reviewers cannot edit syllabus-sourced items in the studio (the
  files are the source of truth); they approve or reject, and corrections go into the files.
- **Content requirements.** `course.yaml` says what each concept needs, verified, before it is
  complete (lesson levels and locales, formulas, shortcuts, patterns, practice and mock
  questions, flashcards), with overrides per subject and per chapter. The coverage report and the
  generation engine both read it.

Commands (from `apps/api`):

```
python -m app.seed.syllabus                 # validate every syllabus and print its size
python -m app.seed.syllabus --partial --subject quant
python -m app.seed --only ssc-cgl           # load it (and the seed courses whose concepts it reuses)
```

The SSC CGL exam profiles are the single source for the exam stages: the Python arithmetic pilot
course reads its Tier 1 profile from `exam_profiles.yaml` too.

## Policy and serving

- `courses.status`: `draft` courses (SSC CGL until its coverage is complete) are hidden from the
  public list, the course page and enrolment for everyone but staff.
- `courses.content_policy`: `open` courses let a learner ask the AI for a missing lesson (saved
  as a draft others then see, labelled). `reviewed_only` courses serve verified content only:
  no drafts and no learner-triggered generation. A concept used by several courses follows the
  strictest of them.
- `GET /concepts/{id}/study-pack` returns the formula sheet, shortcuts, exam patterns (with PYQ
  counts), the PYQ analysis (by year and tier) and the strategies of the concept's chapter and
  subject, all from stored, verified rows: no AI call. It carries a weak ETag and
  `Cache-Control: private, max-age=300`, so browsers revalidate cheaply (304). Staff can pass
  `preview=true` to include items in review.
- Practice draws from the `practice` pool only; mock tests prefer the `mock` pool.

## Previous-year questions

`POST /admin/pyq/imports` takes one paper per file, JSON or CSV, with `dry_run` to validate
without writing. The upload is parsed at once (bad JSON/CSV, missing paper details or licence are
refused with 422); rows are processed by the `pyq.import` job with checkpoints every 50 rows.

```json
{
  "paper": {
    "key": "ssc-cgl:tier1:2024-09-09:s1", "exam": "ssc-cgl", "tier": "tier1", "year": 2024,
    "exam_date": "2024-09-09", "shift": "1", "source": "SSC answer key and question paper",
    "source_url": "https://…", "licence": "public-government-document"
  },
  "questions": [
    {"number": 1, "stem": "…", "options": [{"id": "a", "text": "…"}, …], "answer": "b",
     "explanation": "…", "concepts": ["percentage-marks"], "pattern": "percentage-marks:two-students",
     "difficulty": "medium", "pool": "practice", "steps": {"hint": "…", "solution": "…"}}
  ]
}
```

CSV columns: `number, section, qtype, stem, option_a … option_e, answer, explanation, concepts`
(`;`-separated)`, pattern, difficulty, pool, hint, concept, approach, solution, shortcut,
mistakes`; the paper is sent alongside.

- **Licence** is required: `public-government-document`, `owned`, `licensed` or
  `permission-granted`.
- **Keys:** `pyq:<paper key>:<number>`, so re-importing a corrected file updates in place; a
  changed question goes back to review, an unchanged one keeps its status.
- **Duplicates:** stems are fingerprinted (case, spacing, punctuation and digit grouping
  ignored); a question already in the bank, or repeated within the file, is reported, not stored.
- **Mapping:** a pattern implies its concept; rows without a concept are imported unmapped and
  listed at `GET /admin/pyq/unmapped`, then mapped with `POST /admin/questions/{id}/mapping`.
- Everything arrives `in_review`.

## Coverage

`GET /admin/courses/{slug}/coverage[?scope=subject|subject.chapter]` returns, per subject and
chapter, how many concepts are complete and what is still missing (verified), the concept list
for a scope, and for each exam stage whether the mock pool can fill the planned mocks
(`mock_targets` × questions per section). The course is `ready` when every concept is complete;
publishing stays a deliberate staff decision.

## PR #6 plan: AI content generation engine

Goal: fill the SSC CGL syllabus to its content requirements with AI-generated drafts that
reviewers approve, at a predictable cost, without ever generating the same thing twice.

### Scope

1. **Generation planner.** `plan(course, scope, assets)` reads `concept_gaps()` (coverage) and
   produces work items such as "lesson level 3 for percentage-marks", "6 practice questions for
   pattern percentage-marks:two-students" or "flashcards for writs". It skips anything already
   verified or in review, so re-running a plan after a partial run only fills what is missing.
2. **Batch jobs.** `generate.plan` fans out per chapter into the existing `content` queue with
   checkpoints per concept (the PR #2 job machinery), the per-queue concurrency cap and the
   organisation spend cap (PR #4). Staff start a run for a course, subject or chapter and see
   its progress and cost in the studio.
3. **Grounded prompts per asset type.** New tasks in `app/ai/engines/` for the advanced lesson
   with `solving_method`, formula sheet completion, shortcuts tied to a pattern, pattern
   discovery, question sets per pattern (practice and mock pools kept apart), detailed six-step
   solutions, flashcards and memory tricks. Each prompt gets the concept summary, its
   prerequisites, the authored formulas and patterns, verified PYQs of the concept as style
   examples, and the exam profile; `Task.system` stays static so prompt caching keeps working.
   Telugu follows English once the English lesson is verified.
4. **Automatic checks before review.** Quant answers recomputed where a generator or a solver
   can check them; option and answer-key validation (`validate_item`); duplicate detection by
   stem hash against the whole bank; length and reading-level limits; banned claims (no "this
   was asked in 2023" unless mapped to a PYQ). Failing items are dropped or retried, never queued
   for review.
5. **Review at scale.** Queue filters by course, subject, chapter and asset type; bulk approve of
   a reviewed sample; a sampling policy per asset type (decision needed, see below); reviewer
   throughput and rejection reasons on the Overview tab, fed back into the prompts.
6. **Document grounding (moved from the original PR #5).** S3 storage for source material,
   PostgreSQL full-text search over chunks, and async `ingest.document` jobs, so prompts can cite
   licensed books and notes. Embeddings (bge-m3) stay in the following PR.
7. **Sectioned full mocks.** Build Tier 1 and Tier 2 mocks from the mock pool by the exam
   profile's sections (subject, questions, marks, negative marks, per-section timer), once the
   coverage report shows the pool is ready.
8. **Eval set.** With API keys: a small graded set per engine (lesson, questions, examiner,
   tutor) and `python -m app.ai.check --live`, before tuning effort or prompts.

### Estimates

About 6–8 focused developer-days for the engine (items 1–5, 7, 8), 2–3 more for document
grounding (item 6). The full SSC CGL run costs roughly **USD 500–1,000** in model calls with
caching (about 900 concepts × lessons, ~25 questions, flashcards and sheets each, plus retries),
and needs reviewer time: about 1–2 minutes per question and 5 per lesson, which is the real
bottleneck.

### Decisions needed before PR #6

1. **Source material:** which books or notes may ground generation, and under which licences.
2. **PYQ source:** where previous papers come from (SSC's published papers and keys, a licensed
   vendor, or in-house) and who checks the licence.
3. **Reviewers and sampling:** who reviews (subject experts per subject?) and whether reviewers
   check every item or a sample per batch (e.g. 100% of lessons, 20% of questions with automatic
   rejection of the batch above an error rate).
4. **Telugu scope:** which content is translated in the first pass (lessons only, or questions
   too).
5. **Budget:** confirm the generation budget and the daily spend cap during the run.
6. **Launch staging:** publish SSC CGL subject by subject as coverage completes, or all at once.

Until these are decided, PR #6 uses: no external sources (syllabus + verified PYQs only), full
review of lessons and a 25% sample of questions, English first, a USD 50/day cap, and subject by
subject publishing.
